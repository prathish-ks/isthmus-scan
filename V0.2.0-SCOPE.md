## T0 — Fix first: the kernel-liveness check probes the wrong path

**This is a correctness bug in shipped v0.1.0, and it blocks v0.2.0.**

`src/checks/isthmus-mode.ts` probes `<target>/data/nanogo-kernel.sock`. That is
not where the socket lives. Per `src/config.ts:77-80` and
`src/install-slug.ts:42-52`, the real path is:

```
${XDG_RUNTIME_DIR || os.tmpdir()}/nanoclaw-${sha1(projectRoot).slice(0,8)}/nanogo-kernel.sock
```

It was moved off `DATA_DIR` deliberately — a Unix socket path caps at 104 bytes
on macOS/BSD, and a checkout can live arbitrarily deep.

Effect today: on a healthy Isthmus install, the check reports
`warn` — *"the kernel doesn't appear to be running, so nothing above is actually
being enforced right now"*. A false alarm, on the one check that exists to tell
the operator the kernel is real. Reproduce the slug with `crypto.createHash('sha1')`
and honour `NANOCLAW_KERNEL_SOCKET` (already done) plus the `.env` fallback
(not done — `config.ts` reads both).

## T1 — Headline feature: egress-lockdown wiring (the ADR-024 bug class)

This is the strongest thing to bring across, and it is squarely the README's
pitch: *what your agents can actually reach, not what you assumed.*

PR #47 + ADR-024/025 fixed a silent regression: `NANOCLAW_EGRESS_LOCKDOWN=true`
created and maintained the isolated `--internal` network (host-sweep kept
calling `ensureEgressNetwork()` on a 60s tick, so `docker network ls` looked
exactly right) but **no container was ever attached to it**. Every agent
container sat on the default bridge with unrestricted egress. A check that only
asked "does the network exist" stayed green throughout.

Four sub-checks, all read-only, none spawning a container:

1. **Intent.** Is lockdown expected? Read `NANOCLAW_EGRESS_LOCKDOWN` from env
   *and* from the checkout's `.env` — `src/config.ts:114` honours both, while
   the Go backstop (ADR-025) only sees real env vars. A lockdown set only in
   `.env` is invisible to that backstop; that asymmetry is itself worth an
   `info`.
2. **Ground truth.** `docker ps --filter label=nanoclaw-session -q`, then
   `docker inspect` each container's `NetworkSettings.Networks`. Lockdown on and
   any agent container on `bridge` instead of `NANOCLAW_EGRESS_NETWORK`
   (default `nanoclaw-egress`) → `fail`, with the container name. This is the
   exact assertion the EC-08 gate makes, at a fraction of the cost.
3. **Version detection.** Does `src/modules/kernel-supervisor/index.ts` in this
   checkout export `dockerNetworkArgs` / pass `-docker-network`? A pre-#47
   checkout with lockdown on *is* the silent-open-egress condition even with no
   containers running.
4. **Conflict + gateway.** `NANOCLAW_KERNEL_DOCKER_NETWORK` set to a value other
   than `EGRESS_NETWORK` while lockdown is on → the kernel now refuses to start
   (ADR-024); flag it before the operator hits it. And
   `docker network inspect nanoclaw-egress` → is `ONECLI_GATEWAY_CONTAINER`
   attached? If not, agents are isolated *with no route out* — a distinct,
   reportable degraded state.

Intellectual credit where due: sub-check 3 is ADR-028's `wiring-registry-check`
idea — *assert a claimed enforcement has a live caller* — reduced to something a
scanner can do statically.

## T2 — Supply-chain posture (cheapest to build: pure file reads, no Docker)

Straight from `docs/SECURITY.md` §"Supply Chain Security (pnpm)". All static:

- `pnpm-workspace.yaml`: `minimumReleaseAge` present and ≥ 4320 (3 days).
- `minimumReleaseAgeExclude`: flag every entry; `fail` on a range or wildcard
  (the doc requires an exact pinned version plus human sign-off).
- `onlyBuiltDependencies`: flag entries beyond the shipped set — each one is a
  package permitted to execute arbitrary code at install time.
- `.npmrc`: `minReleaseAge` fallback present.
- `package.json`: `packageManager` pinned to an exact version.

Worth noting as validation of the check's value: Isthmus has drift here right
now. `docs/SECURITY.md` lists `better-sqlite3`, `esbuild`, `protobufjs`, `sharp`
as the `onlyBuiltDependencies` allowlist; `pnpm-workspace.yaml` actually carries
only the last three. Harmless in this direction (the doc over-states), but it is
exactly what this check surfaces.

## T3 — Agent-image pinning

`versions.json` pins `agent-image` by digest
(`...nanoclaw/agent@sha256:79ac5063...`). Two checks:

- **Static:** is `agent-image` pinned by digest, or a floating tag? A tag can be
  repointed at different bytes with nothing in the checkout changing.
- **Live, read-only:** `docker image inspect` the configured image and compare
  its digest against the `versions.json` pin — catches an install running an
  image that no longer matches what it claims to pin.

This is the same discipline as Isthmus's own `egress-image-watch` job (which
greps the pinned `alpine:3.20` digest out of `egress.go` and compares it to Hub)
and PR #44's *pin `govulncheck`, don't float on `@latest`*.

## T4 — Hardened runtime class (a near-verbatim port)

`nanogo doctor`'s ADR-021 check (`go-host/internal/doctor/doctor.go`,
`checkRuntimeClass`) reads `docker info --format
'{{.DefaultRuntime}};{{range $name, $_ := .Runtimes}}{{$name}} {{end}}'` —
read-only, spawns nothing, same cost as the runtime check next to it. Port the
gVisor/Kata/Sysbox substring table and, importantly, its posture:

- hardened runtime is the default → `pass`
- hardened runtime installed but **not** default → `warn` (the one case an
  operator can act on)
- no hardened runtime available → `pass`, plainly worded

That last one matters. The Go comment is explicit: warning every personal
install about a gap it was never promised would be noise. Carry the honesty
across with the logic.

## Explicit non-goals

State these in the README so the tool's boundary stays legible:

- **No `iptables`/DOCKER-USER inspection.** `internal/egress`'s `Check` needs a
  helper container run `--network host --cap-add NET_ADMIN` — by its own comment
  the most privileged container Isthmus runs. A free trial scanner must not.
  The existing `info`-level egress check stays as-is.
- **No dependency auditing.** `npm audit`/`bun audit` need network egress, which
  contradicts "nothing leaves your machine", and duplicate what the repo's own
  CI already gates. T2's static config checks are the honest substitute.
- **No live-container smoke tests.** EC-05/EC-07/EC-08 build images and run
  45-minute jobs. Out of scope for "a few hundred lines you can read before you
  run it."

## Two structural changes v0.2.0 needs

1. **`isthmusEnforced: boolean` is no longer expressive enough.** The
   egress-lockdown check has a third state: *NanoClaw enforces this itself, once
   you are on a version that carries the #47 fix.* That is neither
   "Isthmus kernel enforces it" nor "your own config either way". The README's
   honesty claim — "the report says which is which" — depends on this field, so
   widen it (e.g. `enforcement: 'isthmus-kernel' | 'nanoclaw-native' | 'unenforced'`)
   rather than stretching the boolean. Breaking change to the JSON contract;
   the skill parses it, so update `.claude/skills/isthmus-scan/SKILL.md` in the
   same release.
2. **Reading Docker changes the tool's claim.** Today: "it opens files that
   already exist" plus one local socket probe. T1/T3/T4 add `docker ps`,
   `docker inspect`, `docker info` — still strictly read-only and still nothing
   leaving the machine, but no longer "just files". Update the README and
   `src/index.ts`'s header comment, and make every Docker-dependent check
   degrade to `skip` when the daemon is unreachable so the exit code stays
   CI-safe (non-zero on `fail` only).

## Suggested sequencing

- **v0.2.0**: T0 (bug fix), T2 (static, cheap), T3 static half, plus the
  enforcement-field widening. No Docker dependency yet — ships fast.
- **v0.3.0**: T1 and T4, introducing the Docker read surface together with the
  README honesty update and the `skip`-on-no-daemon discipline.

Splitting this way means the breaking JSON change and the bug fix land before
the tool grows a new dependency class.
