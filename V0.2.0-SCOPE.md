# isthmus-scan v0.2.0 — scope

Priorities, in order:

1. **Value to a stock upstream NanoClaw install** (`nanocoai/nanoclaw`, no Isthmus).
2. **Migration compatibility** — a check must mean the same thing before and
   after a NanoClaw → Isthmus migration, so the two scans are comparable.

Sources: `nanocoai/nanoclaw` @ `c313d06` (v2.4.0) and `prathish-ks/isthmus` @
`1d26826` (PR #49 merge, v2.3.0 base), both read directly.

## What is upstream and what is Isthmus — verified, not assumed

Present in **both**, identical path and format:

| Surface | Upstream | Isthmus |
|---|---|---|
| `~/.config/nanoclaw/mount-allowlist.json` | `config.ts:69` | `config.ts:61` |
| `container/Dockerfile` (`USER node`) | line 140 | present |
| `versions.json` (`agent-image` digest pin) | present | present |
| `pnpm-workspace.yaml`, `.npmrc` | present | present |
| `src/egress-lockdown.ts`, `docs/SECURITY.md` | present | present |

Isthmus-only: `go-host/`, `src/modules/kernel-supervisor/`.

**This table is the whole migration-compatibility story.** Every check below
except kernel liveness reads a file that exists, at the same path, in the same
format, on both sides. That is what makes a before/after scan meaningful.

## Correction to the previous draft

I earlier described the ADR-024 egress-lockdown wiring gap as a NanoClaw
problem. It is not. Upstream's attach path is **live**: `src/drivers/index.ts:80`
`dockerNetworkArgs(spec)` → `ensureEgressNetwork(spec.networkAccess)` →
`egressNetworkArgs()`, registered as `networkArgsFor` and evaluated per spawn.
The regression was introduced by **Isthmus's own EC-02 refactor**, which moved
`docker create` behind the Go kernel and left that closure orphaned. Upstream
never had it.

That changes the check's job, not its value — see U4.

# Part A — Upstream-first features

## U1. Supply-chain config *shape* (headline; pure file reads, no Docker) — SHIPPED in v0.2.0

The strongest upstream feature, because upstream already had this exact bug and
fixed it. Read upstream's own `pnpm-workspace.yaml` comment:

> Top-level, NOT nested under a `pnpm:` key: pnpm reads a `pnpm:` config block
> only from package.json. Nested here in pnpm-workspace.yaml the setting is
> silently ignored (`pnpm config get minimumReleaseAge` returns undefined with
> the nested form, 4320 once hoisted), so the supply-chain release-age gate was
> a no-op.

A 3-day release-age gate defending against typosquatting and compromised
maintainers, present in the file, reviewed, documented in `docs/SECURITY.md` —
and doing nothing. Exactly the "looks configured, silently isn't" shape this
whole tool exists for, and it is upstream's own bug, not Isthmus's.

**Live proof the check is worth building: this repo's own parent has it right
now.** `prathish-ks/isthmus`'s `pnpm-workspace.yaml` carries the nested form:

```yaml
pnpm:
  minimumReleaseAge: 4320     # silently ignored
```

Upstream hoisted it to top level; the fork is on a 2.3.0 base and never picked
the fix up. The Isthmus install's release-age gate is a no-op today.

Checks:

- `minimumReleaseAge` present **and at top level**, ≥ 4320. Nested under
  `pnpm:` → `fail`, because the value looks right and does nothing. Ground truth
  if pnpm is on PATH: `pnpm config get minimumReleaseAge` returns `undefined`.
- `minimumReleaseAgeExclude`: flag every entry; `fail` on a range or wildcard
  (`docs/SECURITY.md` requires an exact pinned version plus human sign-off).
- `onlyBuiltDependencies`: flag entries beyond upstream's set (`esbuild`,
  `protobufjs`, `sharp`). Each is a package allowed to execute arbitrary code at
  install time.
- `.npmrc` `minReleaseAge` fallback present; `package.json` `packageManager`
  pinned exactly.

Note while building: `docs/SECURITY.md` lists `better-sqlite3` in the
`onlyBuiltDependencies` allowlist; neither upstream's nor the fork's
`pnpm-workspace.yaml` actually carries it. Doc over-states, harmless direction —
but do not derive the expected set from the prose.

## U2. Mount-allowlist exposure — keep, and sharpen — SHIPPED in v0.2.0

Already shipped. I re-verified it is still load-bearing on upstream v2.4.0:
`mountAllowed` in `src/drivers/types.ts:628` returns `true` **unconditionally**
for `allowlisted-extra` — *"Vetted upstream by the mount-allowlist feature."*
The spec validator does not re-check; the single vetting point is
`validateAdditionalMounts` at `src/container-runner.ts:1180`.

So the allowlist file really is the only thing between an operator-configured
extra mount and the agent container, on current upstream. The existing check's
framing holds. Sharpen the `detail` to say that plainly — it is a stronger,
more current claim than the PR reference alone.

## U3. Agent-image digest pin (static + one read-only Docker call) — static half SHIPPED in v0.2.0

Upstream `versions.json` pins `agent-image` by digest
(`...nanoclaw/agent@sha256:79ac5063...`). Two checks, both upstream-native:

- Is it pinned by digest, or a floating tag? A tag can be repointed at different
  bytes with nothing in the checkout changing.
- `docker image inspect` the configured image, compare its digest to the pin —
  catches an install running an image that no longer matches what it claims.

Same discipline as upstream's `verify-agent-image.yml` ("gate on the one file
that decides what other people's machines execute") and Isthmus's
`egress-image-watch`.

## U4. Egress-lockdown ground truth (regression detector, not a bug report)

Upstream's wiring is live, so this check does **not** tell an upstream user they
are broken. It confirms their lockdown intent actually took effect — the thing
that silently stopped being true inside Isthmus for an entire release cycle, and
that no amount of `docker network ls` would have revealed.

- Intent: `NANOCLAW_EGRESS_LOCKDOWN` from env **and** the checkout's `.env`
  (`src/config.ts:114` honours both).
- Ground truth: `docker ps --filter label=nanoclaw-session -q`, then
  `docker inspect` each container's `NetworkSettings.Networks`. Lockdown on and
  an agent container on `bridge` instead of `NANOCLAW_EGRESS_NETWORK` (default
  `nanoclaw-egress`) → `fail`, naming the container.
- Gateway route: `docker network inspect nanoclaw-egress` → is
  `ONECLI_GATEWAY_CONTAINER` attached? If not, agents are isolated with no route
  out — a distinct, reportable degraded state.

**Do not skip this:** upstream v2.4.0 returns `[]` from `dockerNetworkArgs` when
`spec.networkAccess.target.kind === 'session-container'`. That is a legitimate
no-network case, not a leak. A check that ignores it produces false positives on
stock upstream — which would be worse than not shipping it.

## U5. Hardened runtime class (near-verbatim port, zero Isthmus dependency)

`doctor.go`'s `checkRuntimeClass` (ADR-021) is one read-only `docker info
--format '{{.DefaultRuntime}};{{range $name, $_ := .Runtimes}}{{$name}} {{end}}'`.
Port the gVisor/Kata/Sysbox substring table **and its posture**:

- hardened runtime is the default → `pass`
- installed but **not** default → `warn` (the one actionable case)
- none available → `pass`, plainly worded

That last one matters. The Go comment is explicit that warning every personal
install about a gap it was never promised is noise an operator cannot honestly
act on. Nothing here needs `go-host/`, so upstream users get it too.

## U6. Non-root containers — keep as-is

Already shipped, upstream-accurate (`container/Dockerfile:140`, `USER node`).

# Part B — Migration compatibility (NanoClaw → Isthmus)

## M1. Fix the kernel-socket path — this is a migration bug — SHIPPED in v0.1.1

`src/checks/isthmus-mode.ts:22` probes `<target>/data/nanogo-kernel.sock`. The
real path (Isthmus `config.ts:77-80`, `install-slug.ts:42-52`) is:

```
${XDG_RUNTIME_DIR || os.tmpdir()}/nanoclaw-${sha1(projectRoot).slice(0,8)}/nanogo-kernel.sock
```

Moved off `DATA_DIR` deliberately — a Unix socket path caps at 104 bytes on
macOS/BSD and a checkout can live arbitrarily deep.

Consequence: a user who **successfully** migrates is told *"the kernel doesn't
appear to be running, so nothing above is actually being enforced."* The tool
fails precisely at the moment it is supposed to confirm the migration worked.
This is the single highest-priority fix in this document. Reproduce the slug with
`sha1(projectRoot).slice(0,8)` and honour `NANOCLAW_KERNEL_SOCKET` from both env
and `.env`.

## M2. Report migration state, not a boolean — SHIPPED in v0.2.0

`detectIsthmus()` keys on `go-host/` existing. A user mid-migration — cloned, Go
kernel never built or never started — reads as "Isthmus" and gets a scary warn.
Report three explicit states instead:

- **not migrated** — no `go-host/`. Plain NanoClaw; U1–U6 all apply.
- **migrated, not enforcing** — `go-host/` present, no `nanogo` binary or socket
  unreachable. Config checks still valid; say clearly that nothing is enforced at
  request time yet, and that this is the expected state before first start.
- **migrated, enforcing** — socket answers. Config checks valid *and*
  continuously enforced.

## M3. Widen `isthmusEnforced` — the field migration depends on — SHIPPED in v0.2.0

A boolean cannot express U1/U3/U5, which are NanoClaw-native config with no
Isthmus involvement either way, nor U4, which is *NanoClaw-native upstream and
kernel-enforced under Isthmus*. Replace with:

```ts
enforcement: 'isthmus-kernel' | 'nanoclaw-native' | 'unenforced'
```

This is what makes a before/after scan readable: the same finding, with its
provenance changing across the migration, is the whole point of running it twice.
Breaking change to the JSON contract — `.claude/skills/isthmus-scan/SKILL.md`
parses it, so both move in one release.

## M4. `--baseline` / `--compare` — SHIPPED in v0.2.0

Isthmus's README already promises: *"run it before installing Isthmus to see your
current exposure, and again after to confirm the kernel is actually enforcing."*
The tool cannot currently do that. Add:

```bash
isthmus-scan --json > before.json     # on plain NanoClaw
isthmus-scan --compare before.json    # after migrating
```

Diff by check name: level changes, and `enforcement` transitions. This is the
migration story as a feature rather than a sentence in someone else's README,
and it is cheap — the JSON report already carries everything needed.

# Non-goals — state these in the README

- **No `iptables`/DOCKER-USER inspection.** `internal/egress`'s `Check` needs a
  helper container run `--network host --cap-add NET_ADMIN`, by its own comment
  the most privileged container Isthmus runs. A free read-only scanner must not.
  The existing `info`-level egress check stays.
- **No dependency auditing.** `npm/pnpm/bun audit` need network egress, breaking
  "nothing leaves your machine", and duplicate CI both projects already run. U1's
  static config checks are the honest substitute.
- **No live-container smoke tests.** EC-05/EC-07/EC-08 build images and run
  45-minute jobs.
- **No repo-development gates.** `semgrep`, `go-lint`, `coverage-gate`,
  `performance-gate`, `wiring-registry-check` measure the repo, not an install.
  (`wiring-registry-check`'s *idea* — assert a claimed enforcement has a live
  caller — is the seed of U4, reduced to something a scanner can do.)

# Sequencing

**v0.1.1 — done.** M1 alone. Verified side by side on one healthy install with a
kernel bound at the real runtime-dir path: the old check reports `WARN`, the new
one `PASS`. The legacy `data/` path is still probed last, so pre-relocation
installs keep passing and say so.

**v0.2.0 — done.** U1, U2 sharpening, U3 static half, M2, M3, M4. Every check is
still a plain file read, so the README's "opens files that already exist" claim
stays true and the tool needs no daemon.

Verified against both real checkouts rather than fixtures: upstream
`nanocoai/nanoclaw` v2.4.0 passes all three new checks; `prathish-ks/isthmus`
FAILS the release-age gate on its own nested `pnpm:` form, naming line 7. The
`--compare` path was exercised upstream-baseline → fork, and against a
synthesized v0.1.x baseline.

One correctness point found while building it: a v0.1.x baseline carries no
`enforcement` field, so deriving one from its boolean marked all six checks
"changed" on the first upgrade. Those deltas are now skipped, with the report
saying enforcement was not comparable — 1 real change instead of 5 phantom ones.

**v0.3.0 — the Docker read surface.** U3 live half, U4, U5, introduced together
with two honesty updates: the README and `src/index.ts`'s header both currently
claim the tool only "opens files that already exist", and every Docker-dependent
check must degrade to `skip` when the daemon is unreachable so the exit code
stays CI-safe (non-zero on `fail` only).

Ordered this way, a stock-NanoClaw user gets real value at v0.2.0 without
installing anything or running a daemon, and the breaking field change lands
before the tool grows a new dependency class.

# Possible upstream contribution

Two of these are upstream's own gaps, already reasoned about in upstream's own
comments, and would fit `ncl`/CI rather than a third-party scanner:

- **U1 as a CI gate.** Upstream fixed the nested-`minimumReleaseAge` no-op by
  hoisting the key, but nothing stops it regressing — and forks inherit the
  broken shape, as this repo's parent shows. A few lines asserting
  `pnpm config get minimumReleaseAge` is defined would pin it permanently.
- **U2.** `nanocoai/nanoclaw#3680` is already filed. Worth noting in that thread
  that v2.4.0's `mountAllowed` still returns `true` unconditionally for
  `allowlisted-extra`, so the single-vetting-point property is unchanged.
